# E1: 앱 형태 문서로 잰 하이브리드 무게

`docs/milestones.md` E1의 기록이다. F2는 하이브리드 검색(`ask`: 상위 5개, 목록마다 후보 20개)의 기본 무게(벡터 0.2 / BM25 0.8)가 BM25 후보에 없는 정답을 버리는 "벽"을 찾았고, KoEn-E5-Tiny 레시피에 0.5/0.5를 권했다([`../f2-fusion/README.md`](../f2-fusion/README.md)). 그 근거 자료는 위키백과, 공개 보고서, 의학·생명과학 논문 초록이었다. 이 문서는 앱이 실제로 넣을 법한 문서(제품 도움말, 앱 FAQ·릴리스 노트, 사내 규정·회의록, 긴 PDF)와 질문으로 같은 비교를 다시 한 결과다. 엔진 기본값과 레시피 값은 바꾸지 않았다.

> **질문 검수.** 질문 120개는 세션이 쓴 초안이다. 2026-11-14 세션이 원문과 대조해 판정을 적었고, 같은 날 사용자가 그 판정을 확정했다(`author: session_draft+human_review`). 판정은 OK 106개, 고침 14개(질문 13, 정답 구절 1), 빼기 0개다. 이 문서의 수치는 모두 검수를 반영한 뒤 다시 잰 것이다. 검수표와 고친 이유는 [`review_sheet.md`](review_sheet.md), 검수 전 수치와의 비교는 아래 "검수 전후".

## 결론

- **KoEn-E5-Tiny: 0.5/0.5가 기본값보다 낫다. 레시피와 같은 방향이다.** 답 있는 90개 중 71 → 80(+10/−1, 부호 검정 p ≈ 0.012). 영어 34 → 38, 한국어 37 → 42이고, 조정용 절반(33 → 38)과 확인용 절반(38 → 42) 모두 같은 방향이다. 0.6/0.4는 이 자료에서 0.5/0.5와 같다(80).
- **MiniLM(기본 모델): 0.5/0.5가 조금 못하다.** 60 → 57(+2/−5, p ≈ 0.45). 영어는 35 → 36(+2/−1)으로 거의 같고 한국어는 25 → 21(+0/−4)로 준다. MiniLM은 영어 전용이라 한국어 벡터 검색이 거의 못 찾는다(벡터만 2/45). F2에서 본 모양과 같아서, 이 결과도 MiniLM의 기본값을 바꿀 근거가 되지 않는다.
- **BGE-m3(참고): 0.5/0.5가 낫다.** 72 → 80(+9/−1, p ≈ 0.02), 0.6/0.4는 82. F2의 영어 논문 자료에서는 0.2와 0.5가 같았던 모델이다(429 대 429). 레시피를 만들지 않은 모델이라 기록만 한다.
- **얻은 몫은 거의 모두 "다른 낱말로 묻는 질문"에서 나온다.** 낱말이 겹치는 질문은 세 모델 모두 기본값에서 이미 거의 다 맞고(영어 19/20, 한국어 KoEn·BGE-m3 20/20), 0.5/0.5에서 잃은 것은 모델마다 0~1개다.
- **벽은 이 자료에도 있다.** 영어 질문은 60개 모두 BM25 20개 목록이 찼고, 목록이 찬 질문에서 기본값 상위 5개는 세 모델 모두 100% BM25 후보였다.
- **답 없는 질문은 RRF 점수로도, 벡터 유사도 하나로도 가를 수 없다.** 30개 모두 상위 5개가 채워져 나왔고, 대부분 앱 문서·사내 문서의 비슷한 주제 청크가 1위였다. 벡터 1위 유사도도 답 있는 질문과 많이 겹친다(아래 표).
- **검수로 기본값이 올랐고 0.5/0.5의 이득은 조금 줄었다.** 고친 질문은 실제 사용자가 쓰는 낱말(trash, factory reset, USB, 할부)로 바뀌어 BM25가 더 찾는다(BM25만 59 → 64). KoEn은 기본값 66 → 71, 0.5/0.5 76 → 80으로, 이득이 +10에서 +9로 줄었다. 고치지 않은 78개의 결과는 세 모델 모두 검수 전과 같다.
- **확신: 중간.** 방향(KoEn·BGE-m3에서 0.5가 낫고, MiniLM 한국어에서 잃음)은 세 갈래 나눔(언어, 조정/확인, 문서 종류)에서 같은 쪽이고 검수 뒤에도 같아서 높게 본다. 크기는 낮게 본다. 질문과 문서 일부(직접 쓴 24개)를 같은 세션이 썼고, 검수는 판정 확정이지 사용자가 질문을 새로 쓴 것이 아니다. 답 있는 질문이 90개뿐이라 언어별 차이는 대부분 통계로 가를 수 없다.

## 벽: 이 자료에서도 BM25 목록이 차는가

| 실행 | BM25 20개 목록이 찬 질문 (영어 / 한국어, 각 60) | 찬 질문의 기본값 상위 5개 중 BM25 후보 | 벡터만 맞고 기본값 틀림 (그중 BM25 목록 참) | 그중 0.5 / 0.6이 되찾음 |
|---|---|---|---|---|
| MiniLM | 60 / 38 | 490 / 490 | 영어 6 (6), 한국어 0 | 영어 2 / 3 |
| KoEn | 60 / 37 | 485 / 485 | 영어 6 (6), 한국어 6 (4) | 영어 4 / 4, 한국어 6 / 6 |
| BGE-m3 | 60 / 37 | 485 / 485 | 영어 9 (9), 한국어 6 (4) | 영어 4 / 6, 한국어 5 / 5 |

- 영어는 "the", "how" 같은 흔한 낱말 하나만 맞아도 BM25 후보가 되어 60개 모두 목록이 찼다(엔진 BM25가 불용어를 빼지 않는 것은 D1에서 본 대로다). 한국어는 문서가 56개뿐이라 MIRACL(212/213)보다 덜 찼다.
- 한국어에서 KoEn·BGE-m3가 벡터만 맞힌 6개를 기본값에서 잃었는데, 그중 2개는 BM25 목록이 안 찬 질문이다. 목록이 덜 차도 BM25 쪽 무게 0.8이 벡터 1위를 밀어낸다.

| BGE-m3 | 10/2/3 · 14/1/0 | 같음 | 영어 0.553 / 0.654, 한국어 0.564 / 0.638 | 영어 11/15, 한국어 15/15 |

- 유사도는 1 − (엔진이 돌려준 벡터 거리)다.
- 30개 모두 상위 5개가 채워져 나왔다. 0.2에서 0.5로 바꾸면 1위 문서가 30개 중 4~6개에서 바뀌었다(MiniLM 4, KoEn 6, BGE-m3 5). 표의 종류별 수는 거의 그대로다.
- 1위는 30개 모두 같은 언어의 문서였고, 대부분 비슷한 주제의 앱·사내 문서였다(KoEn 예: "What is the warranty period for the Lumo Hub?"에 Lumo 허브 Wi-Fi 문제 해결 문서, "출장 가기 전에 경비를 미리 받을 수 있나요?"와 "출장 일정이 주말에 걸리면 휴일 근무로 인정되나요?"에 국내 출장비 정산 규정). 2026-11-09 게임 가이드 연동에서 본 것처럼, 작은 생성 모델이 이런 가까운 문서로 답을 지어낼 수 있다.
- 벡터 1위 유사도는 답 있는 질문과 많이 겹친다. 답 없는 질문의 73~100%가 "벡터로 맞힌 답 있는 질문 중 가장 낮은 유사도"보다 높았다. 유사도 기준값 하나로 거르면 답 있는 질문을 함께 버린다. 이 측정으로는 거르는 신호를 정할 수 없고, 후보 목록의 "관련 없는 질문 거르기 신호"에 근거로 남긴다.

## example 앱

E1과 같은 PR로 example 앱을 바꿨다(범위는 `docs/milestones.md` E1).

- **모델 선택:** `--dart-define=EXAMPLE_MODEL=minilm|koen`. Model Pack(`assets/models/<이름>/model-pack.json`)으로 초기화한다. KoEn이면 레시피대로 `defaultVectorWeight: 0.5, defaultBm25Weight: 0.5`를 넣고, MiniLM은 엔진 기본값을 쓴다. 모델마다 DB 파일을 따로 쓴다. 상태 카드에 모델, 언어, 차원, 무게를 보인다.
- **"App docs" 화면:** E1 문서 56개를 `e1_app_docs` 컬렉션에 넣고(하네스와 같이 자산을 파일로 복사해 `addDocumentFromFile`), 질문 120개를 언어·유형별로 고르거나 직접 입력해 상위 5개를 본다. 무게(앱 기본, 0.2/0.8, 0.5/0.5, 0.6/0.4, 벡터만, BM25만)를 바꿔 볼 수 있고, 목록의 질문이면 정답이 상위 5개에 들었는지 표시한다. 검색은 하네스의 `ask` 조건과 같은 `searchMeta(topK: 5)`다.
- **`example/README.md`:** 모델 준비 안내를 Model Pack과 KoEn 레시피로 고쳤다(전에는 BGE-m3를 curl로 받는 안내였다).
- **앱 확인:** `example/integration_test/e1_app_docs_parity_test.dart`가 앱 코드로 문서를 넣고 질문 120개 × 무게 6개를 돌려, 결과를 하네스 덤프와 비교한다([`scripts/e1/compare_app_parity.py`](../../../scripts/e1/compare_app_parity.py), 실행은 [`scripts/e1/run_app_parity.sh`](../../../scripts/e1/run_app_parity.sh)). 앱은 macOS profile 빌드로 빌드됐다(Model Pack 두 개와 PDF를 넣어 162.8MB).

| 모델 | 앱 기본 | 0.2/0.8 | 0.5/0.5 | 0.6/0.4 | 벡터만 | BM25만 | 기본 = 레시피 명시 |
|---|---|---|---|---|---|---|---|
| MiniLM (앱 기본 = 0.2/0.8) | 60 | 60 | 57 | 43 | 40 | 64 | 120/120 (2개는 첫 호출에서 달라 다시 불러 같음) |
| KoEn (앱 기본 = 0.5/0.5) | 80 | 71 | 80 | 80 | 79 | 64 | 120/120 (2개는 첫 호출에서 달라 다시 불러 같음) |

- 수치는 하네스 덤프의 오프라인 계산과 무게마다 같다.
- "첫 호출에서 다름"은 같은 무게로 두 번 불러도 생기는 차이로 보고(BM25 동점 순서), 테스트는 다섯 번 안에 한 번이라도 같으면 같다고 센다. 동점 순서는 후보 목록에 적었다.

## 다시 만들기

```bash
python3 scripts/e1/build_e1_bundle.py            # cargo로 PDF 글과 BM25 토큰을 뽑는다
scripts/eval/run_passage_eval.sh --model <MiniLM pack dir> --name e1_minilm --bundle e1 --dump-candidates --out build/eval_results/e1_minilm
scripts/eval/run_passage_eval.sh --model <KoEn dir> --name e1_koen --bundle e1 --dump-candidates --out build/eval_results/e1_koen
scripts/eval/run_passage_eval.sh --model <BGE-m3 dir> --name e1_bgem3 --bundle e1 --dump-candidates --out build/eval_results/e1_bgem3
python3 -I scripts/e1/e1_report.py build/eval_results/e1_minilm build/eval_results/e1_koen build/eval_results/e1_bgem3 --json docs/perf/e1-app-docs/results_e1.json
python3 -I scripts/eval/f7_fusion_compare.py build/eval_results/e1_minilm build/eval_results/e1_koen build/eval_results/e1_bgem3
scripts/e1/run_app_parity.sh koen   # 모델 파일을 example/assets/models/koen/에 둔 뒤
python3 -I scripts/e1/compare_app_parity.py build/eval_results/e1_app_koen/e1_app_parity_koen.json build/eval_results/e1_koen
```

GNOME 도움말 쪽을 다시 받으려면 `example/assets/corpus/e1/gnome/gnome_pages_v1.json`의 URL을 받아 `python3 -I scripts/e1/gnome_help_to_md.py --raw <dir> --out example/assets/corpus/e1/gnome`로 바꾼다. 쪽은 그 뒤 바뀌었을 수 있으니 `raw_sha256`으로 같은지 확인한다.

# F2-0: 고칠 형태 비교 (2026-11-14)

`docs/milestones.md` F2의 첫 단계다. 엔진을 고치지 않고, F1에서 남긴 후보 덤프 10개를 다시 결합해 고칠 형태 (A)~(D)를 비교했다. **이 결과로 기본값을 바꾸지 않았다(규칙 10.3).** 고를 형태는 사용자가 정한다.

## 결론

1. **(D) 후보 수 늘리기는 효과가 없다.** 무게 0.2에서 후보를 50~400개로 늘려도 MIRACL 조정용 합계가 336 → 333~335, 확인용이 335 → 330~331이다. 버리는 문제가 풀리지 않는다. 뺀다.
2. **(C) 모든 모델에 같은 새 기본값은 이득이 작은 것만 남는다.** 벡터 비중을 올리는 방식은 모두 MiniLM(영어 전용 기본 모델)의 한국어 질의를 잃는다(80개 묶음 한국어 32개 중 RRF 0.5와 정규화 선형 0.5 모두 −3, RRF 0.6은 80개 전체에서 −25). 어디서도 거의 잃지 않는 것은 "RRF 0.2 + 벡터 1위가 2위보다 거리 0.05 이상 앞설 때만 자리 보장"뿐이고, MIRACL 조정용 +12/−0, 확인용 +10/−0으로 3%p 남짓이다. 그 0.05는 모델마다 거리 분포가 달라 사실상 모델별 값이다.
3. **(B) 모델에 따른 무게가 이 자료에서 가장 낫다.** 다국어 모델(KoEn-E5-Tiny, BGE-m3)에 RRF 0.6(벡터 0.6 / BM25 0.4)을 쓰면 확인용 합계가 KoEn 166 → 182(+17/−1), BGE-m3 169 → 190(+21/−0)이고, 80개 묶음(+1/−0, +5/−1)과 F1 묶음(+7/−0, +8/−0)에서도 나빠지지 않는다. MiniLM은 지금 0.2를 그대로 둔다. 무게는 이미 `ask`·`search*`의 인자라 **결합 코드를 새로 쓰지 않아도 된다.** 남는 것은 그 값을 어디에 두느냐다(아래 "정할 것").
4. **(A) 새 결합 방식(정규화 선형, 자리 보장)은 (B)보다 뚜렷이 낫지 않다.** BGE-m3에서는 정규화 선형 0.7이 가장 높지만(확인용 196, +30/−3), KoEn 1.5만에서 잃는 질의가 늘어난다(정규화 선형 0.7 확인용 −8). 엔진 코드가 필요한데 이득이 모델마다 엇갈린다.

**확신:** (D)를 빼는 것과 (C)의 이득이 작다는 것은 높다(모든 자료에서 같은 방향). (B)가 낫다는 것은 중간이다. 다국어 모델 둘이 MIRACL train으로 미세조정됐고, 80개·F1 묶음은 질의가 적으며, 답 없는 질문에 무엇을 넘기는지는 재지 않았다.

## 고른 방법과 주의

- 값은 MIRACL 조정용 106개(5천·1.5만 두 실행 합계 212)만 보고 고르고, 확인용 107개로 확인했다. 질의 id는 `scripts/miracl/miracl_ko_ids_v1.json`.
- **조정용 합계만 최대로 하면 두 모델 모두 정규화 선형 0.7이 뽑힌다.** KoEn에서 그것은 확인용에서 9개를 잃는다(RRF 0.6은 1개). 이 보고서는 "조정용에서 잃는 질의가 적은 것"을 함께 보고 RRF 0.6을 앞에 뒀다. 이 기준은 **결과를 본 뒤에 적은 것**이라, F2에서 값을 확정할 때는 학습에 쓰이지 않은 자료로 다시 확인해야 한다.

## 읽는 법과 한계

- **(D)는 근사다.** 후보 K개는 덤프된 400개 목록의 앞 K개로 만들었다. 엔진은 K마다 다른 ef로 HNSW를 찾으므로 결과가 다르다. 실제로 400개 목록의 앞 20개가 엔진의 20개 목록과 같은 질의는 실행마다 14/32~176/213이다. 그래도 무게 0.2에서 후보 400개까지 이득이 없다는 방향은 계산(벡터 단독 1위 `0.2/61`이 BM25 단독 185위 아래로만 이긴다)과 맞는다.
- **학습 겹침:** KoEn의 바탕 모델 multilingual-e5-small과 BGE-m3는 MIRACL train으로 미세조정됐다. 벡터 비중을 올리는 방식의 MIRACL 이득이 부풀려졌을 수 있다. 80개·F1 묶음은 그 영향이 없지만 작다.
- **답 없는 질문:** F1 묶음의 8개에서 방식마다 무엇을 1위로 넘기는지는 재지 않았다. 벡터 비중을 올리면 주제만 같은 청크가 올라올 수 있다.
- **같은 덤프 위의 비교**라 HNSW를 새로 만들 때의 흔들림(한두 질의)은 방식 사이 차이에 들어가지 않는다. 다른 실행과 비교할 때는 들어간다.
- 결합 검증(덤프 재결합이 엔진과 같은지)은 F1에서 같은 덤프로 했다(`f7_fusion_compare.md`, `miracl_ko.md`).

2. **(B)라면 값을 어디에 둘지.** 지금도 `ask(..., vectorWeight: 0.6, bm25Weight: 0.4)`로 부를 수 있지만, 호출마다 넘겨야 하고 레시피에 적혀 있지 않다.
   - (B1) 레시피·가이드에만 적는다. 코드 변경 없음. 앱이 잊으면 지금과 같다.
   - (B2) `MobileRag` 초기화 때 기본 무게를 한 번 정하는 인자를 연다(규칙 10.1의 "인자를 열기"). 값은 앱이 정하고 레시피가 권한다. 기본은 지금 0.2/0.8.
   - (B3) Model Pack 메타데이터에 권장 무게를 둔다. 지금 Model Pack은 MiniLM 하나뿐이고 KoEn은 레시피로 받으므로 당장은 쓸 데가 없다.
3. **확인 자료:** 학습에 쓰이지 않은 한국어 자료로 RRF 0.6을 한 번 더 확인할지(내려받기는 허락이 필요하다).

## 한 줄 요약

기본 하이브리드는 BM25가 고른 후보 20개 안에서만 순서를 바꾼다. 한국어에서는 그 20개가 거의 항상 차 있어서, BM25 후보에 없는 정답은 벡터 검색이 1위로 찾아도 결과에 들지 못한다. F2는 앱이 초기화 때 무게를 정할 수 있게 하고, KoEn-E5-Tiny 레시피(한국어·영어 문서)가 0.5/0.5를 쓰게 했다. 기본값 0.2/0.8은 바꾸지 않았다.

## 원인

설정 세 가지가 겹쳤다. 코드(`rust_builder/rust/src/api/hybrid_search.rs` `compute_hybrid_rrf_scores`, `lib/src/internal/defaults.dart`)와 덤프로 확인했다.

1. **결합은 순위만 쓰는 RRF다.** 점수는 `0.2/(60+벡터 순위) + 0.8/(60+BM25 순위)`이고 기본 무게는 벡터 0.2, BM25 0.8이다.
2. **`ask`는 목록마다 후보 20개만 본다.** topK 5에 컬렉션 필터가 있어 후보가 4배가 된다.
3. **한국어 BM25 목록은 거의 항상 20개로 찬다.** 한국어는 두 글자 단위(바이그램)로 토큰을 만들어 흔한 조각 하나만 맞아도 후보에 든다. MIRACL 213개 질의 중 212개에서 찼다(네 실행 모두).

그래서:
- 벡터에만 있는 1위 청크는 `0.2/61 ≈ 0.0033`, BM25에만 있는 20위(꼴찌) 청크는 `0.8/80 = 0.0100`이다. BM25 목록이 차 있으면 벡터에만 있는 청크는 상위 5개에 들 수 없다. 이 벽은 벡터 무게가 61/141(≈ 0.433) 이하일 때 생긴다.
- 실제로 기본값 상위 5개 1,065자리 중 1,060자리가 BM25 목록의 청크였다. 벡터 검색은 BM25가 고른 20개의 순서만 바꿨다.

| 같음, 1.5만 구절 | KoEn-E5-Tiny | 176 | 150 | 165 |

- 섞은 결과가 벡터 검색 혼자보다 나빴다. 벡터가 찾은 정답의 16~19%(31~37개)를 버렸고, 대부분 질문과 정답이 낱말을 일부만 공유하는 질의였다.
- F1 묶음의 낱말이 전혀 안 겹치는 13개에서는 벡터가 10개를 찾았지만 기본값에는 4개가 남았다.
- MIRACL 논문에서는 BM25와 mDPR을 섞은 쪽이 각각보다 좋았다(한국어 nDCG@10 0.419 / 0.419 → 0.609). 제대로 섞으면 어느 한쪽보다 나아지는 것이 보통이다.

## 원인이 아닌 것 (확인함)

- **VABQ:** 모든 측정의 fingerprint가 `f32+vabq:none`이다. 꺼져 있었다.
- **벡터 검색(HNSW, i8 양자화):** 같은 색인의 벡터 검색만으로는 잘 찾았다. 손실은 합치는 단계에서 생긴다. i8 검색은 PR6 측정에서 recall@10 약 0.997로 거의 손실이 없다.
- **엔진 구현 버그:** 엔진이 낸 벡터·BM25 후보 목록을 덤프해 Python으로 RRF만 다시 계산하면 질의별 정답 순위가 엔진과 2,125~2,127/2,130건(실행마다) 같다. 다른 건은 모두 BM25 점수 동점이다(엔진은 동점 순서를 `HashMap`에서 정한다). 계산은 설계대로다.
- 별개의 작은 손실: `ask` 조건의 HNSW `ef_search`가 100이라 가장 가까운 청크를 가끔 놓친다. F2 범위 밖에 남겼다.

## 왜 이 기본값이었나

- 0.5/0.5에서 0.2/0.8로 바꾼 커밋은 `5f506d7`(2026-02-14, "improve hybrid retrieval quality")이고 근거가 적혀 있지 않다.
- 지키는 경우가 있다. 기본 모델 MiniLM은 영어 전용이라 한국어에서 벡터가 약하다. 80개 묶음 MiniLM에서 벡터 무게를 0.6으로 올리면 한국어 32개 중 정답이 27개에서 8개로 무너진다. W1은 "좋은 값이 모델마다 반대"라는 이유로 바꾸지 않았다.
- 그 대가로, 다국어 모델을 쓰는 앱은 벡터 검색을 거의 쓰지 못했다.

## 왜 지금까지 보이지 않았나

- **평가 질의가 쉬웠다.** 그때까지의 판단은 80개 묶음에 기댔는데, 그 질의는 모두 정답과 낱말이 겹친다(안 겹침 0개). BM25만으로도 대부분 찾았다.
- **측정 조건이 실제 사용과 달랐다.** README 수치는 topK 100, 즉 목록마다 후보 400개로 잰 값이다. 후보가 400개면 벡터 1위(`0.0033`)가 BM25 400위(`0.8/460 ≈ 0.0017`)를 이길 수 있어 벽이 드러나지 않는다. 실제 `ask`의 후보 20개 조건은 F1(F-3)에서 처음 쟀다.

### F2-0에서 고른 이유 (요약)

- **(D) 후보 수 늘리기:** 무게 0.2에서 후보 400개까지 늘려도 이득이 없었다. 벽은 후보 수가 아니라 무게에서 온다.
- **(C) 모든 모델에 같은 새 기본값:** 벡터 무게를 올리면 MiniLM의 한국어 정답을 잃는다. 거의 안 잃는 방식("벡터 1위가 뚜렷이 앞설 때만 자리 보장")은 이득이 3%p 남짓이고 기준값이 모델마다 다르다.
- **(B) 모델별 무게:** 다국어 모델에 RRF 0.6은 MIRACL 확인용 질의에서 KoEn +17/−1, BGE-m3 +21/−0이었고 80개·F1 묶음에서도 나빠지지 않았다. 무게는 이미 인자라 결합 코드를 새로 쓸 필요가 없었다. 값은 뒤의 재확인에서 0.5로 바꿨다(아래).
- **(A) 새 결합 방식:** BGE-m3에서는 가장 높았지만 KoEn 1.5만에서 잃는 질의가 늘었다. (B)보다 뚜렷이 낫지 않아 넣지 않았다.
- 주의: 조정용 질의 합계만 최대로 하면 정규화 선형 0.7이 뽑힌다. "잃는 질의가 적은 것"을 함께 본 기준은 결과를 본 뒤에 정했다. 그래서 학습에 쓰이지 않은 자료로 다시 확인했다.

## 남은 것

- **기본값은 여전히 0.2/0.8이다.** 다국어 모델을 쓰면서 `defaultVectorWeight`를 넣지 않는 앱은 그대로다. 레시피와 CHANGELOG로 알린다.
- **하이브리드가 아직 벡터만보다 낮은 경우가 있다.** MIRACL에서는 0.5/0.5도 벡터만보다 낮다(KoEn 5천 182 대 196). 반대로 KorQuAD·AutoRAG에서는 하이브리드가 벡터만보다 높다. 어느 쪽이 실제 앱에 가까운지는 문서와 질문에 달렸다. 다만 두 모델 모두 MIRACL로 미세조정됐고, 줄인 말뭉치와 너그러운 채점(정답 여러 개, 하나만 맞아도 됨)이 벡터에 유리해 벡터 수치가 부풀었을 수 있다.
- **별도 항목:** `ask` 조건의 HNSW 손실(ef 100), 답 없는 질문의 신호(RRF 점수로는 가를 수 없음), 한국어 바이그램 BM25 자체(Q3 B9와 맞물림).

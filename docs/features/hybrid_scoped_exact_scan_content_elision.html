Hybrid Scoped Exact-Scan — Content Projection Elision

Scoped query-path optimization  ·  Branch: codex/scoped-bm25-term-stats (based on main @ d736b30, which includes PR #51 scoped BM25 instrumentation)  ·  Owner: bhoh@polarpulse.ai  ·  Date: 2026-05-17

What changed. The scoped exact-scan branch of hybrid_search (the path triggered by source_ids / metadata_like filters) used to pull c.content for every scoped chunk when BM25 was active. We now keep vector scoring exact by walking scoped embeddings, but retrieve BM25 ranks from the active collection BM25 term index restricted to those scoped chunk ids.

Net effect. Both bm25_weight = 0 and bm25_weight > 0 scoped queries read zero chunk-body bytes and perform zero per-chunk tokenization at query time, while preserving BM25 ranks when the collection BM25 index is active.

Why this mattered. The previous behavior scaled linearly with the scoped set — 500 chunks × ~256 B ≈ 125 KB of SQLite content read per query, even when the bytes were only needed to reconstruct term frequencies that already exist in the BM25 index.

Background

The scoped exact-scan branch is the fallback hybrid search runs when a query carries source_ids or metadata_like filters. Instead of querying global vector / BM25 indexes and post-filtering, it walks every chunk under the scope and re-scores both legs in-process. The current implementation keeps the vector exact scan, then asks the active BM25 index to compute a scoped BM25 rank over the scanned chunk ids.

The legacy SELECT read four columns per row: c.id, c.embedding, c.embedding_i8, c.content. Only the first three are needed for vector scoring; c.content existed solely so the per-row BM25 collector could tokenize the chunk body. That collector has been replaced by indexed scoped BM25 lookup.

The BM25 leg only contributes to the final RRF score when both:

  • config.bm25_weight > 0.0 — otherwise it is multiplied by zero, and
  • tokenize_for_bm25(query_text) returns at least one term — otherwise no chunk can match.

Whenever one of those is false, every byte read from c.content is pure I/O waste. When BM25 is active, the same term frequencies and document lengths are already available in the collection BM25 index after rebuild, so re-reading bodies at query time is also avoidable.

Instrumentation

The scoped body-read and tokenization counters remain in query_metrics as regression guards. They should stay at zero for scoped queries that use indexed BM25:

// rust_builder/rust/src/api/query_metrics.rs
static SCOPED_EXACT_SCAN_CONTENT:      AtomicCounter             = AtomicCounter::new();
static SCOPED_EXACT_SCAN_TOKENIZATION: AtomicTokenizationCounter = AtomicTokenizationCounter::new();

pub struct QueryContentReadStats {
    // … existing fields …
    pub scoped_exact_scan_rows:                    u64,  // SELECT rows that returned content
    pub scoped_exact_scan_content_bytes:           u64,  // bytes read from c.content
    pub scoped_exact_scan_tokenized_rows:          u64,  // rows that fed tokenize_for_bm25
    pub scoped_exact_scan_tokenized_content_bytes: u64,  // bytes handed to tokenizer
    pub scoped_exact_scan_tokens:                  u64,  // tokens produced (post-normalization)
    pub scoped_exact_scan_tokenization_nanos:      u64,  // wall-time spent tokenizing
}

The counters are intentionally not included in rows_total() / content_bytes_total() — those describe materialized result reads, while these measure backend scoped-scan body work. Under indexed BM25, that backend body work should be absent; hydration and assembly counters still record materialized result reads later.

Change

SELECT projection drops content

// rust_builder/rust/src/api/hybrid_search.rs (scoped branch)
let query_tokens = tokenize_for_bm25(&query_text);
// `!= 0.0` (not `> 0.0`) — preserves prior behavior for any non-zero weight,
// including negative values that callers might pass.
let need_bm25 = config.bm25_weight != 0.0 && !query_tokens.is_empty();

let query_with_i8 = format!(
    "SELECT c.id, c.embedding, {}
         FROM chunks c
         LEFT JOIN sources s ON c.source_id = s.id
         WHERE {}",
    "c.embedding_i8",
    exact_conditions.join(" AND ")
);

Notes:

  • The exact scan still walks every scoped embedding to preserve vector recall under source_ids / metadata_like.
  • The fallback prepare (the NULL AS embedding_i8 path used on schemas without the i8 column) also omits c.content.
  • The gate uses != 0.0 rather than > 0.0 so any non-zero weight — including negative weights some callers use as a penalty — still requests BM25 ranks from the term index.

BM25 scoring uses scoped postings

let chunk_iter = stmt.query_map([], |row| {
    Ok((
        row.get::<_, i64>(0)?,
        row.get::<_, Vec<u8>>(1)?,
        row.get::<_, Option<Vec<u8>>>(2)?,
    ))
})?;

let mut scoped_doc_ids = Vec::new();
for row in chunk_iter {
    if let Ok((id, embedding_blob, embedding_i8_blob)) = row {
        // … vector scoring (unchanged) …
        scoped_doc_ids.push(id);
    }
}

if need_bm25 {
    bm25_results = bm25_search_scoped_tokens(&query_tokens, &scoped_doc_ids, candidate_k);
}

bm25_search_scoped_tokens reuses the active in-memory BM25 inverted index, computes document frequency and average document length over the supplied scoped ids, and returns BM25 candidates without touching chunk bodies.

Two signals worth flagging:

  • I/O is gone on the indexed BM25 path: scope 500 drops from 125 KB of SQLite content reads to 0 bytes even with bm25_weight = 0.5.
  • Tokenization moved out of query time. The scoped query now pays the existing BM25 rebuild/indexing cost once, then reuses postings and document lengths for source-scoped ranking.

Behavior we did not change

  • bm25_weight != 0 ranking semantics — BM25 still contributes through RRF, but term frequencies and document lengths now come from the active BM25 index instead of per-query body tokenization.
  • Non-scoped queries — unchanged, the post-filter path doesn't touch content for scoring.
  • Hydration counters (full_hydrate_*, preview_*, assembly_*) — unchanged; those still record materialized result reads in SearchHandle.
  • The collection_id-only filter path still uses post-filter against the global indexes; it does not enter the scoped exact-scan branch.

Compatibility

  • No public API surface changes. SearchFilter, RrfConfig, SearchMetaHybridOptions, and the Dart-side wrappers are byte-for-byte identical for callers.
  • No FRB surface change in this P1 implementation; only Rust internals, benchmark expectations, and documentation changed.
  • Behavior of search_hybrid / search_hybrid_simple / search_hybrid_weighted still depends on active HNSW/BM25 indexes for indexed ranking. Public Dart service entrypoints activate the target collection before search.

Follow-ups

  • Postings observability. Body-read/tokenization counters are now zero on the scoped query path. The next useful metric is BM25 postings scanned per query term so we can decide whether a source-keyed postings map is worth the memory.
  • Index freshness contract. Public SourceRagService entrypoints already call activateCollectionForHybridSearch before search. Direct low-level calls should keep that contract documented, because scoped BM25 now depends on the active collection BM25 index for ranks.
  • Benchmark realism. The fixture uses synthetic 256 B chunks; real chunk bodies are typically 1–4 KB. Absolute query-time body-read savings on a 500-chunk scope scale to 0.5–2 MB per query, and tokenization is now paid during index rebuild rather than during each scoped query.

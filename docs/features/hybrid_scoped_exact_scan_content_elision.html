Hybrid Scoped Exact-Scan — Content Projection Elision

P0 query-path optimization  ·  Branch: enhancement/scoped-exact-scan-elision (rebased onto origin/main @ abf6b7e, which includes PR #49 handle-content-cache)  ·  Owner: bhoh@polarpulse.ai  ·  Date: 2026-05-17

What changed. The scoped exact-scan branch of hybrid_search (the path triggered by source_ids / metadata_like filters) used to pull c.content for every scoped chunk unconditionally. We now elide that column from the SELECT when the BM25 leg cannot contribute to the final RRF score.

Net effect. When callers pass bm25_weight = 0 (or the query produces no BM25 tokens), the scoped exact-scan reads zero chunk bytes regardless of scope size. With bm25_weight > 0 the behavior is unchanged.

Why P0. The previous behavior scaled linearly with the scoped set — 500 chunks × ~256 B ≈ 125 KB of SQLite content read per query, even when the bytes were never tokenized. That growth is independent of top_k, so it dominates large scoped filters.

Background

The scoped exact-scan branch is the fallback hybrid search runs when a query carries source_ids or metadata_like filters. Instead of querying global vector / BM25 indexes and post-filtering, it walks every chunk under the scope and re-scores both legs in-process. This trades index latency for recall on small scoped subsets.

The legacy SELECT read four columns per row: c.id, c.embedding, c.embedding_i8, c.content. Only the first three are needed for vector scoring; c.content exists solely so the per-row BM25 collector can tokenize the chunk body.

The BM25 leg only contributes to the final RRF score when both:

  • config.bm25_weight > 0.0 — otherwise it is multiplied by zero, and
  • tokenize_for_bm25(query_text) returns at least one term — otherwise no chunk can match.

Whenever one of those is false, every byte read from c.content is pure I/O waste.

Instrumentation (landed first)

Before changing behavior we landed two counter families in query_metrics so the I/O cost and the CPU cost are both measurable end-to-end:

static SCOPED_EXACT_SCAN_CONTENT:      AtomicCounter             = AtomicCounter::new();
static SCOPED_EXACT_SCAN_TOKENIZATION: AtomicTokenizationCounter = AtomicTokenizationCounter::new();

pub(crate) fn record_scoped_exact_scan_content_read(content_bytes: u64) { … }

pub(crate) fn record_scoped_exact_scan_tokenization(
    content_bytes: u64,
    tokens: u64,
    elapsed_nanos: u64,
) { … }

pub struct QueryContentReadStats {
    // … existing fields …
    pub scoped_exact_scan_rows:                    u64,  // SELECT rows that returned content
    pub scoped_exact_scan_content_bytes:           u64,  // bytes read from c.content
    pub scoped_exact_scan_tokenized_rows:          u64,  // rows that fed tokenize_for_bm25
    pub scoped_exact_scan_tokenized_content_bytes: u64,  // bytes handed to tokenizer
    pub scoped_exact_scan_tokens:                  u64,  // tokens produced (post-normalization)
    pub scoped_exact_scan_tokenization_nanos:      u64,  // wall-time spent tokenizing
}

The counters are intentionally not included in rows_total() / content_bytes_total() — those describe materialized result reads, while these measure backend scan work. A scoped chunk that survives RRF is read once during the scan and (if needed) once again during hydration; conflating them would double-count.

The tokenization counter is a separate atomic family because it answers a different question than the I/O counter. After this P0 lands, scoped_exact_scan_content_bytes becomes zero on the elided path, but the bm25-on path still pays the tokenization cost proportional to scope size, not top_k — that signal is what surfaces the next P1 candidate.

Change

SELECT projection becomes conditional

// rust_builder/rust/src/api/hybrid_search.rs (scoped branch)
let query_tokens = tokenize_for_bm25(&query_text);
let query_token_set: HashSet<String> = query_tokens.iter().cloned().collect();
// `!= 0.0` (not `> 0.0`) — preserves prior behavior for any non-zero weight,
// including negative values that callers might pass.
let need_bm25 = config.bm25_weight != 0.0 && !query_token_set.is_empty();
let content_projection = if need_bm25 { "c.content" } else { "NULL AS content" };

let query_with_i8 = format!(
    "SELECT c.id, c.embedding, {}, {}
         FROM chunks c
         LEFT JOIN sources s ON c.source_id = s.id
         WHERE {}",
    "c.embedding_i8",
    content_projection,
    exact_conditions.join(" AND ")
);

Notes:

  • The token set is computed once, before the SQL prepare, and the same predicate guards both the projection and the post-scan BM25 scoring block.
  • The fallback prepare (the NULL AS embedding_i8 path used on schemas without the i8 column) goes through the same projection.
  • The gate uses != 0.0 rather than > 0.0 so any non-zero weight — including negative weights some callers use as a penalty — keeps the prior behavior of reading content and computing BM25. We only elide when the BM25 contribution to RRF is provably zero.

Row reader treats content as nullable

let chunk_iter = stmt.query_map([], |row| {
    Ok((
        row.get::<_, i64>(0)?,
        row.get::<_, Vec<u8>>(1)?,
        row.get::<_, Option<Vec<u8>>>(2)?,
        row.get::<_, Option<String>>(3)?,   // was: String
    ))
})?;

for row in chunk_iter {
    if let Ok((id, embedding_blob, embedding_i8_blob, content)) = row {
        if let Some(ref content_str) = content {
            record_scoped_exact_scan_content_read(content_str.len() as u64);
        }
        // … vector scoring (unchanged) …

        if need_bm25 {
            if let Some(content_str) = content {
                // … existing BM25 token / df / tf collection …
            }
        }
    }
}

The counter only fires when content was actually pulled. The post-scan scoring block also flips its guard from !query_tokens.is_empty() to need_bm25, so the two gates stay in lockstep.

Two signals worth flagging:

  • I/O is gone on the elided path: scope 500 drops from 125 KB to 0 bytes of SQLite content reads, and wall-clock from 2.73 ms to 0.76 ms — ~3.6× faster on the same fixture for the most common scoped query shape (vector-only re-ranking under source_ids).
  • Tokenization scales with scope, not top-K. 50→500 scope grows tokens 1,705→17,050 (10×) and tokenize time 0.181→1.588 ms (~8.8×), confirming the P1 candidate flagged in the follow-ups section: when bm25_weight != 0 and top_k is tiny, we still tokenize every body in the scope. A scoped BM25 index keyed by source — or even a precomputed per-chunk term-stats blob — would cut this to O(top_k) instead of O(scope).

Behavior we did not change

  • bm25_weight != 0 path — identical reads, identical ranking. Verified by test_scoped_exact_scan_skips_content_when_bm25_disabled (top-K is stable). Includes negative weights (treated as a BM25 penalty by RRF); they keep the previous body-reading behavior intact.
  • Non-scoped queries — unchanged, the post-filter path doesn't touch content for scoring.
  • Hydration counters (full_hydrate_*, preview_*, assembly_*) — unchanged; those still record materialized result reads in SearchHandle.
  • The collection_id-only filter path still uses post-filter against the global indexes; it does not enter the scoped exact-scan branch.

Compatibility

  • No public API surface changes. SearchFilter, RrfConfig, SearchMetaHybridOptions, and the Dart-side wrappers are byte-for-byte identical for callers.
  • FRB struct shape gained trailing query-metric fields. P0 added scoped exact-scan read rows/bytes; P1 adds tokenized rows/bytes, token count, and tokenization time. The native dylib and Dart bindings must be rebuilt together — older clients pinned to the previous bindings will fail to decode the stats struct.
  • Behavior of search_hybrid / search_hybrid_simple / search_hybrid_weighted is unchanged for every input that previously produced a ranked result; only the SQL projection and a counter are different.

Follow-ups (P1 candidates, now quantified)

  • P1: scoped BM25 indexing. The tokenization counter now puts a number on the previously-hand-wavy "we tokenize 500 bodies to score 4 winners" claim — at 256 B / chunk we see 17,050 tokens / 1.588 ms per query on the 500-chunk scope, roughly 58% of the bm25-on wall-clock budget (1.588 / 2.73 ms) and growing linearly with scope size. Two viable directions:
    • Precomputed per-chunk BM25 term stats stored alongside the chunk row, so the scan reads stats not bodies.
    • A scoped BM25 inverted index keyed by source_id (or collection_id) so the scan only touches documents that contain query terms — turning O(scope) into O(top_k).
  • Per-token String allocation. Orthogonal to this change; still tracked as the copy-elision candidate from the same triage. The scoped_exact_scan_tokens counter now provides the lower-bound allocation count to compare against any allocation-free alternative.
  • Benchmark realism. The fixture uses synthetic 256 B chunks; real chunk bodies are typically 1–4 KB. Absolute scan-bytes savings on a 500-chunk scope scale to 0.5–2 MB per query (not 125 KB), and tokenize-time scales with body length — so the production ROI on a vector-only scoped query is materially larger than the synthetic numbers above.

Mobile RAG Engine 온디바이스 데이터 마이그레이션 계획

대상 패키지: mobile_rag_engine 0.18.4 동반 패키지: rag_engine_flutter 0.18.2 문서 기준: 2026-05-17 KST 범위: 사용자 디바이스에 영속화되는 4개 데이터 표면

결론

현재 CREATE TABLE IF NOT EXISTS와 hnsw_rs 크레이트의 파일 포맷에 암묵적으로 의존하고 있다. 신규 인스톨과 업그레이드 인스톨이 구분되지 않고, 임베딩 모델을 바꿔도 stale 임베딩과 새 임베딩이 silently 섞일 수 있다.

해결 방향은 SQL 스키마 · HNSW 파일 · BM25 stats · 임베딩 fingerprint를 독립 axis로 버저닝하고, 단일 매니저가 Apply / Rebuild / Invalidate 세 가지 결정을 내리도록 만드는 것이다. 자동 폐기 금지는 1.0의 신뢰 라인이다.

없음 현재 PRAGMA user_version 또는 메타테이블
in-memory 임베딩 dimension 베이스라인 영속화 상태
P0 4-axis fingerprint + embedding gate 우선순위
fixture past-version DB로 부팅 회귀 테스트가 production gate

현재 상태 진단

데이터 표면 현재 처리 위험 코드 위치
SQLite 스키마 CREATE TABLE IF NOT EXISTS만 사용. PRAGMA user_version 설정/체크 없음 컬럼 추가는 가능하지만 컬럼 변경/삭제 불가. 신규 인스톨과 업그레이드 인스톨 구분 불가 rust_builder/rust/src/api/db_pool.rs:62, source_rag.rs:256-404

설계 핵심: 4-axis fingerprint + 단일 매니저

하나의 거대한 db_version으로 묶지 않는다. SQL 스키마, HNSW 파일, BM25 stats, 임베딩 모델 fingerprint는 변화 주기와 회복 전략이 모두 다르다. migration_meta 테이블 하나에 4개 axis를 따로 저장한다. 

migration_meta:
  key                      | value
  -------------------------+---------------------------------
  sql_schema_version       | 5
  hnsw_format_version      | 2
  bm25_stats_version       | 1
  embedding_fingerprint    | "all-MiniLM-L6-v2|384|qint8_arm64"
  last_engine_version      | "0.18.4"

엔진 부팅 시 매니저가 4개 axis에 대해 다음 세 결정 중 하나를 내린다.

결정 의미 적용 표면 사용자 영향
Apply forward migration 실행 (예: ALTER TABLE ADD COLUMN) SQL 스키마의 비파괴 변경 투명 — 부팅 latency만 약간 증가
Rebuild SQLite 데이터는 보존하고 derived index만 재생성 HNSW 포맷 변경, BM25 알고리즘 변경 cold start 1회 길어짐. 검색 결과는 동일
Invalidate 데이터 폐기 + 사용자 명시 액션 요구 임베딩 fingerprint 불일치 (사용자가 모델 교체) 검색/ingest 잠금 + reembedAll() 또는 clearAndRestart() 호출 필요

핵심 원칙: Invalidate는 자동 실행 금지. 사용자 데이터를 자동으로 폐기하지 않는 것이 1.0의 신뢰 라인이다. RagError.embeddingFingerprintMismatch를 throw하고 사용자가 명시적 액션을 호출할 때까지 검색/ingest API를 잠근다.

우선순위별 작업 카드

P0

1. migration_meta 테이블 + 4-axis 버전 backbone

모든 후속 작업이 의존하는 최소 backbone. 기존 인스톨은 “v0”으로 간주하고 첫 부팅에 backfill.

  • SQL: migration_meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)
  • Rust: MigrationManager::read_axes() / write_axis()
  • Dart: MobileRag.instance.migrationState 읽기 전용 surface
  • 관측 가능성: 부팅 시 4개 axis 값을 structured log로 emit
P0

2. 임베딩 fingerprint 검증 게이트

가장 위험한 케이스 — 사용자가 모델 교체. 자동 폐기 금지, 명시적 confirm 필요.

  • 부팅 시 stored vs current fingerprint 비교
  • 불일치 → RagError.embeddingFingerprintMismatch(stored, current) throw, search/ingest 잠금
  • 사용자 액션: reembedAll(progress:) 또는 clearAndRestart()
  • 두 경로 모두 resumable — 중간 종료해도 다음 부팅에 이어서
P1

3. Forward-only SQL 마이그레이션 시스템

기존 CREATE TABLE IF NOT EXISTS들을 v0001_init.sql로 응고하고, 이후 변경은 번호 부여.

  • 마이그레이션 스크립트를 Rust 바이너리에 임베드
  • 각 스크립트는 idempotent + 트랜잭션 안에서 axis 업데이트까지
  • downgrade 미지원 (모바일에 다운그레이드 경로가 사실상 없음)
  • 기존 인스톨의 v0 ≡ v1 매핑 정확도가 핵심 위험 지점
P1

4. HNSW 파일 envelope + 자동 rebuild

crate 포맷에 위임하지 말고 자체 envelope을 둔다. SQLite 임베딩 BLOB만 살아있으면 결정적 복원 가능.

  • 4-byte magic + hnsw_format_version + crate version 문자열 + payload
  • envelope 불일치 → 파일 폐기 + rebuild_from_sql() 트리거
  • 사용자 시점에서는 “첫 검색이 느림” 수준의 영향
  • 한 번 envelope이 들어가면 이후 변경이 비싸짐 — 초기 디자인이 핵심
P2

5. BM25 stats versioning

알고리즘이 바뀔 일이 드물어 가장 마지막. 그러나 토크나이저 정책 변경 시 게이트로 필요.

  • bm25_stats_version axis bump만으로 in-memory rebuild 강제
  • collection별 cache 폐기 정책 명확화
  • 현재는 알고리즘 변경 자체가 적어 priority 낮음
P2

6. Fixture 기반 회귀 테스트 (production gate)

“과거 버전 DB 파일로 현재 코드 부팅 시 정상 동작”을 CI에 박는다. 이게 진짜 안전망.

  • test/native/fixtures/v0_18_4/ 같은 디렉터리에 SQLite + HNSW + BM25 스냅샷
  • 릴리즈 시점마다 fixture 추가
  • CI 잡: fixture로 엔진 부팅 → migration 적용 → 표본 검색 일치 검증
  • fixture 자산 크기 증가는 비용. 보존 범위는 사용자가 슬라이더로 조절

의사결정 기준

질문 판단 기준 설계 영향
마이그레이션을 자동으로 적용할 것인가? 비파괴 (Apply, Rebuild)는 자동. 파괴 (Invalidate)는 사용자 명시. API 레벨에서 게이트 여부가 갈림. autoVsManual 슬라이더로 조절 가능.
cold-start latency를 어디까지 허용? HNSW rebuild는 corpus 크기 비례. UI에서 progress 노출 여부와 묶임. warm-up 정책, deferIndexWarmup 기본값, lazy rebuild 트리거 시점.
downgrade를 지원할 것인가? 모바일 패키지에서 다운그레이드 경로가 사실상 없음 → No. 스크립트는 forward-only. axis 값이 “현재 코드가 모르는 더 큰 숫자”면 부팅 거부.
fixture를 몇 버전까지 보존? 릴리즈 cadence와 자산 크기의 함수. fixtureBackVersions 슬라이더로 조절. 0이면 fixture 회귀 미도입, 6이면 최근 6 minor 보존. CI 시간/자산 비용 증가.
사용자 UI 노출 정도 silent log → debug warning → host app 콜백 → blocking dialog. userVisibility 슬라이더로 조절. 패키지는 채널만 노출, UI는 host app 책임.

Gate 정의

마이그레이션 PR의 기본 gate: (1) migration_meta 변경이면 새 인스톨 + 기존 인스톨(v0 backfill) 두 경로 모두 부팅 테스트. (2) embedding_fingerprint 게이트가 영향받는 변경이면 mismatch 시 검색/ingest가 잠기는지 native test로 고정. (3) HNSW envelope 변경이면 envelope mismatch 시 자동 rebuild → 검색 결과 동일성 검증. (4) 모든 axis 변경은 PR description에 before/after 4-axis 값을 표로 첨부.

주의: Invalidate 결정이 새로 추가되는 PR은 반드시 사용자 시점의 시나리오 문서를 동반한다. 자동 폐기는 1.0 약속을 깬다.

레드라인: 사용자 디바이스의 임베딩 BLOB을 명시적 confirm 없이 삭제하는 경로가 코드에 한 곳이라도 있으면 PR을 머지하지 않는다.
